## Three Vitest projects

Tests run as three separate Vitest projects across two config files rather than one flat suite:

- **`storybook`**: configured in <RepoFile path="vitest.config.ts" />, runs every story
  Storybook picks up in a real Chromium browser via `@vitest/browser-playwright`. The globs live
  in <RepoFile path=".storybook/main.ts" />: `src/**/*.stories.@(js|jsx|mjs|ts|tsx)` plus
  `src/**/*.mdx`, so docs pages authored as MDX are part of the same run. Stories are the primary
  component test harness in this repo: write a story to cover a component's states, and that story
  doubles as its test. Run with:

  ```bash
  pnpm test:storybook
  ```

- **`unit`**: configured in <RepoFile path="vitest.node.config.ts" />, runs `*.test.ts` files
  under `src/` (excluding integration tests) and the `*.test.mjs` files next to the custom ESLint
  rules in `eslint-rules/`, all under Node. Run with:

  ```bash
  pnpm test
  ```

- **`integration`**: also configured in <RepoFile path="vitest.node.config.ts" />, runs
  `*.integration.test.ts` files, capped at a single worker with extended hook and test timeouts
  because each suite spins up real infrastructure. Run with:

  ```bash
  pnpm test:integration
  ```

Both `unit` and `integration` resolve the `@` path alias to `src/`, matching the app's <RepoFile
path="tsconfig.json" /> alias. It is declared once, in the top-level `resolve.alias` of <RepoFile
path="vitest.node.config.ts" />, and inherited by both projects, not repeated per project. The
`storybook` project in <RepoFile path="vitest.config.ts" /> declares no alias of its own; it gets
module resolution from the Storybook Vite setup instead.

## Integration test harnesses

Integration suites do not open a database connection by hand; they use a shared harness under <RepoFile
path="src/test/postgres-integration-harness.ts" />. `createPostgresIntegrationHarness` starts a
fresh Postgres Testcontainers instance, runs Drizzle migrations against it, and returns a `db`
client plus helpers for counting, listing, and truncating tables. `createAuthIntegrationHarness` in <RepoFile
path="src/test/auth-integration/harness.ts" /> wraps that base harness with auth-specific helpers on
top.

The typical lifecycle: create the harness once in `beforeAll`, reset the tables it touches in
`afterEach`, and dispose of it once in `afterAll`.

```ts
import { afterAll, afterEach, beforeAll, describe, it } from 'vitest';

import { createAuthIntegrationHarness } from '../test/auth-integration/harness';

describe('example integration suite', () => {
  let harness: Awaited<ReturnType<typeof createAuthIntegrationHarness>>;

  beforeAll(async () => {
    harness = await createAuthIntegrationHarness();
  });

  afterEach(async () => {
    await harness.resetAuthTables();
  });

  afterAll(async () => {
    await harness.dispose();
  });

  it('uses migrated db', async () => {
    const counts = await harness.getAuthCounts();
    // assertions...
  });
});
```

The `integration` Vitest project loads <RepoFile path="src/test/setup-integration.ts" /> before any
suite runs, which applies base auth test environment settings shared by every integration test.

## Images in stories

Route every image through `next/image`, never a raw `{'<img>'}` tag or a CSS `url(/…)` reference.
A story that breaks this rule renders fine locally and 404s on the published gallery. The Tokens &
styling rules page states the rule and why the published subpath makes it load-bearing.

## Type-checking, linting, and formatting

`pnpm check` runs the full local gate in one command: type-checking, ESLint, Stylelint, Prettier's
check mode, and the duplicate-arbitrary-value scan (see the Tokens & styling rules page). Run it
before opening a pull request. It is a subset of what CI enforces, not a mirror: CI's Quality job
also runs `pnpm build` and the unit tests, and the Storybook, Integration, and docs jobs run on top
of that.

## Story gates enforced by ESLint

Two of the repo-local ESLint rules, registered under the `potrzebnik` plugin in <RepoFile
path="eslint.config.mjs" /> and implemented in `eslint-rules/`, guard the story harness itself.
Like every rule in `eslint-rules/`, each ships with a `RuleTester` suite in the `unit` project.

- `potrzebnik/require-colocated-story` applies to `.tsx` files under `src/components/ui/` and
  `src/components/shared/`. A component with no `*.stories.tsx` neighbour is never rendered by
  `pnpm test:storybook`, so nothing checks it and the axe gate never sees it.
- `potrzebnik/valid-story-viewport` applies to `*.stories.tsx` and rejects an unknown key pinned as
  `globals.viewport.value` — the shape the runtime actually reads — or as the legacy
  `parameters.viewport.defaultViewport`. An unknown key is not a runtime error: the viewport
  silently falls back to 1200x900, so a story named "Mobile" quietly renders — and gets tested — as
  desktop. The key must be a static string literal, otherwise the gate has nothing to check.

Allowed keys are `MINIMAL_VIEWPORTS` from `storybook/viewport` plus the keys of `viewportOptions`
in <RepoFile path=".storybook/viewports.mjs" />. That module is the single source of the project's
viewport options: <RepoFile path=".storybook/preview.tsx" /> uses it as
`parameters.viewport.options`, and the rule reads its keys, so adding a viewport in one place is
enough.

## Component naming enforced by ESLint

`potrzebnik/component-filename-convention` guards the filenames under <RepoFile
path="src/components" /> instead of the story harness, so it is registered twice — once per
convention — with its own `files` section.

- Under `src/components/ui/` it requires a kebab-case basename and nothing else. That directory is
  the shadcn CLI's output directory declared in <RepoFile path="components.json" />: renaming its
  files means the next `shadcn add button` drops a second `button.tsx` beside `Button.tsx`.
- Under `src/components/sections/`, `src/components/shared/`, and `src/components/features/` it
  requires a PascalCase basename **and** a component export of that exact name, resolved from the
  `export` nodes rather than from the source text. A file the project owns is named after the
  component it exports, so an import path reads the same as the symbol it binds. The export half is
  skipped for `*.stories.tsx` and for `ui/`, whose files export several primitives at once.

The `convention` option is required, so a new directory cannot be added to the rule without stating
which of the two conventions it follows.
