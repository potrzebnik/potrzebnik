## Styling model

Style components with Tailwind utility classes co-located directly in JSX. The repository has no
hand-written component CSS and no BEM-style class names; a component's styling lives next to its
markup, not in a sibling stylesheet. Tailwind v4 is wired in through the PostCSS plugin at <RepoFile path="postcss.config.mjs" />, not a `tailwind.config.js`.

## Design tokens, not raw colours

Every colour used in a component must resolve through a design token, never a literal `#hex`,
`rgb()`, or `oklch()` value written inline. Tokens are declared once in <RepoFile path="src/app/globals.css" /> under the `@theme inline` block, which
maps each `--color-*` custom property to a CSS variable such as `--background`
or `--header-bg`. The same block also declares the non-colour tokens:
`--font-sans`, `--font-mono`, and the `--radius-*` scale. Add a new colour by
declaring the variable there, then reference it with the matching Tailwind
utility (for example `bg-header-bg`), never by pasting the raw value into a
component.

That split matters for where a literal is allowed to live. The token
definitions under `:root` in <RepoFile path="src/app/globals.css" /> are the one
legitimate home for a raw value, and several of them are plain hex today
(`--overlay-yellow: #f6d94f`, `--help-section-btn-bg: #f6d94f`). What is out of
bounds is a literal on a colour _property_ anywhere else.

<RepoFile path=".stylelintrc.json" /> enforces that mechanically, though more
narrowly than the rule of thumb suggests:

- `selector-class-pattern` rejects any hand-written CSS class name that is not the `.dark` theming
  hook, catching BEM-style classes before they land.
- `declaration-property-value-disallowed-list` rejects values starting with `#`
  or `rgb`, plus numeric-leading `oklch(` (the pattern is `^oklch\(\s*[\d.]`,
  so `oklch(var(--x))` passes), on a fixed list of nine enumerated properties:
  `background`, `background-color`, `color`, `border`, `border-color`,
  `border-top-color`, `border-bottom-color`, `outline`, and `outline-color`. It
  is a fixed list, not a `border*`/`outline*` wildcard: `border-left-color`,
  for instance, is not covered. It also does not apply to custom properties, so
  the token definitions above pass cleanly.

Run `pnpm lint:css` to check `src/**/*.css` locally; the same command runs in CI. In practice that
is a single file: <RepoFile path="src/app/globals.css" /> is the only CSS file under `src/`.

## Arbitrary Tailwind values

A repeated Tailwind arbitrary value (`px-[25px]` used in several places, for example) is a token
that has not been named yet. <RepoFile path="scripts/check-duplicate-arbitrary-values.mjs" />
scans the codebase for spacing and sizing arbitrary values, compares the tally against a committed
baseline, and fails only when a value's count grows past that baseline; pre-existing debt does not
block CI, but new duplication does. Run it directly:

```bash
pnpm check:duplicate-values
```

If a growth is intentional (you are about to promote the value to a real token anyway), accept the
new count explicitly:

```bash
pnpm check:duplicate-values:update-baseline
```

## UI primitives vs feature composites

Three tiers of component live under <RepoFile path="src/components" />:

- <RepoFile path="src/components/ui" /> holds shadcn-style primitives (`button`,
  `card`, `badge`, `popover`, `link`) generated and configured through
  <RepoFile path="components.json" />. Treat these as the base vocabulary:
  extend them rather than reinventing a primitive inline.
- <RepoFile path="src/components/features" /> and
  <RepoFile path="src/components/shared" /> hold composites built out of those
  primitives for a specific part of the product (the public header and footer,
  help cards, section templates).
- <RepoFile path="src/components/sections" /> holds the page-level sections
  assembled from those composites (`AboutSection`, `HelpSection`,
  `OrganizationsSection`).

<RepoFile path="components.json" /> pins the shadcn style (`new-york`), the base
colour, the CSS entry point (<RepoFile path="src/app/globals.css" />
), and the import aliases (`@/components`, `@/components/ui`, `@/lib`,
`@/lib/utils`, `@/hooks`) that new primitives are generated against. Regenerate
or add a primitive through the shadcn CLI so it stays consistent with these
settings, instead of hand-authoring a component under `ui/`.

## Images always go through `next/image`

Route every image through `next/image`: never a raw `<img>` tag and never a CSS `url(/…)` background
reference. The two components that currently render images, <RepoFile
path="src/components/shared/HelpCard.tsx" /> and <RepoFile
path="src/components/shared/SectionTemplate.tsx" />, both import `Image` from `next/image` for this
reason.

The reason is the published gallery. Stories reference assets root-absolutely (`/children.jpg`),
which is correct for the application but resolves against the site origin, not against
`/potrzebnik/storybook/`, once Storybook is deployed under that subpath. Storybook's `next/image`
mock ignores a configured image loader, so the references are rewritten to relative ones in the
built output by <RepoFile path="scripts/rewrite-storybook-asset-paths.mjs" />. That rewrite only
recognises quoted, root-absolute references to files in <RepoFile path="public" />, so a raw
`<img src="/…">` or a CSS `url(/…)` is not covered and will 404 on the deployed gallery.
